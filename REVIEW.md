# REVIEW.md

Defects found in the starter `app/main.py`. All of them are fixed in the submitted version.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Floors the elapsed time to whole minutes *before* applying the 10-minute grace, so the grace boundary is wrong: 09:40:01 for a 09:30 shift returns 0 instead of 10 (R2 is defined in seconds: strictly more than 10:00 late, then floor of minutes since shift start). It also builds shift start by `replace()`-ing the punch's own datetime, which is a naive server-local/UTC value, not the attendance date in IST. | Punch in at 09:40:01 IST and at 00:30 IST; wrong `late_minutes` / wrong day used. | Build the shift-start instant from the attendance date + `shift_start` in IST, compare in seconds (`> 600`), then floor minutes since shift start. |
| 2 | `compute_work_hours` | Uses Python's `round()`: banker's rounding plus binary float error. 9.125 h comes out 9.12; R4 requires half-up, i.e. 9.13. | Punch in/out exactly 9 h 7 m 30 s apart; `work_hours` is 9.12 instead of 9.13. | `Decimal` arithmetic on whole seconds, quantised to 2 places with `ROUND_HALF_UP`. |
| 3 | `compute_overtime` | No 30-minute minimum (R3): any positive overrun is returned, e.g. 5 minutes past shift end gives 5 instead of 0. It also cannot handle overnight shifts — the shift end is always placed on the record's own date, never the next day. | Sample document 1 in DATA_MODEL.md (out 18:35, shift ends 18:30) would report 5 overtime minutes; the sample says 0. Overnight sample 7 happens to pass only because the caller never supplies this helper. | Return the floored minutes only when >= 30; place `shift_end` on date + 1 when the shift is overnight (`shift_end <= shift_start`). |
| 4 | helpers (missing) | No half-day computation (R5), no attendance-date rule (R1, incl. the overnight previous-day rule), and no truncation of instants to whole seconds anywhere. | Overnight punch-in at 01:00 IST; a punch with millisecond fraction .900. | Added `attendance_date_for`, truncation inside the ms→datetime conversion, and half-day from the *rounded* `work_hours`. |
| 5 | `GET /health` | Always returns `{"status": "ok"}` without touching MongoDB. The contract requires 200 only when a ping succeeds, otherwise 503. | Stop MongoDB and call `/health`: starter still says ok. | Run `db.command("ping")`; on any exception return 503. |
| 6 | `POST /employees` | Check-then-insert (`find_one` then `insert_one`) with no unique index anywhere in the app: two concurrent creates with the same `emp_code` both return 201. The contract requires the *database* unique index to decide. | Send 10 identical creates in parallel; more than one 201. | Unique index on `employees.emp_code` created at startup; insert directly and translate `DuplicateKeyError` to 409. |
| 7 | `POST /employees` (validation) | The Pydantic model is all plain `str`: no `emp_code` pattern, no email pattern, no length limits, `joined_on` is never checked as a real date, and `shift_start == shift_end` is accepted. All of these must be 422. | Create with `emp_code: "X"`, `joined_on: "2026-02-30"`, or equal shift times: starter returns 201. | Field patterns/lengths in the model, a real-date validator, and a model validator rejecting equal shift times. |
| 8 | `POST /employees` (`created_at`) | `datetime.now()` is naive *server-local* time, so the stored instant is wrong on any non-UTC host; it is also returned to the client as an ISO string, not epoch milliseconds as the contract requires for every instant. | Create an employee and inspect the response: `created_at` is a string like `"2026-…T…"` instead of an integer. | Store an aware UTC `datetime.now(UTC)` (truncated to seconds) and serialise every instant through one `dt_to_ms` helper. |
| 9 | `GET /employees` | Pagination is off by one — `skip = page * page_size`, so page 1 skips a whole page. `total` is `count_documents({})`, ignoring the `department` filter. There is no sort, although the contract requires `emp_code` ascending. No bounds on `page`/`page_size` (page 0, page_size 1000 accepted). | List with `page_size=2`: the first two employees are missing; filter by a department and `total` still counts everyone. | `skip=(page-1)*page_size`, `total` from the filtered query, explicit sort, `page >= 1`, `1 <= page_size <= 100` (422 otherwise). |
| 10 | `POST /attendance/punch-in` | Unknown employee is not handled: `emp` is `None` and `emp["shift_start"]` raises, producing a 500 instead of 404. | Punch in with `emp_code: "EMP9999"`. | Look the employee up first and raise 404 when absent (same for punch-out and PATCH). |
| 11 | `POST /attendance/punch-in` (time handling) | `datetime.fromtimestamp(ms/1000)` gives naive *server-local* time; the attendance date is `ts.date()` in that zone — not IST, with no overnight rule (R1). A 00:30 IST punch lands on the previous UTC date; a 01:00 IST night-shift punch gets the wrong date entirely. Milliseconds are also kept, violating the truncation rule. | Punch in at 00:30 IST and at 01:00 IST on the 22:00–06:00 shift; compare `date` with DATA_MODEL sample 7. | Convert ms to an aware UTC datetime truncated to seconds; derive the date in IST with the overnight previous-day exception. |
| 12 | `POST /attendance/punch-in` (race + validation) | Check-then-insert race: concurrent punch-ins for the same (employee, date) can both succeed. `punched_at` is a bare `Optional[int]` — a seconds value, float or string is not rejected as the contract demands (422). `status` is a free string, so `ABSENT` or garbage is accepted at punch-in. The response also adds a non-contract `id` field and returns datetimes instead of epoch ms. | Parallel duplicate punch-ins; `punched_at: 1783500000` (seconds); `status: "ABSENT"`. | Rely on the unique `(emp_code, date)` index + `DuplicateKeyError` → 409; `StrictInt` epoch-ms type bounded to [1e11, 4.102e12]; status restricted to the presence enum; response built by the shared serializer (no `_id`/`id`). |
| 13 | `GET /attendance` | Loads the whole filtered collection into Python, sorts in memory, then slices — slow and memory-hungry at ~100k records. The sort itself is wrong: only `date` descending, with no `emp_code` ascending tie-break. No validation of the date filters (`date_from > date_to` must be 422). Legacy documents are returned raw: missing `history`/`half_day`, datetimes instead of epoch ms. | Seed two records on the same date and check their order; call with `date_from` after `date_to`; read sample document 9 (no `history`). | Push filter + sort + skip/limit into MongoDB (backed by the date indexes), validate dates and the range in the endpoint, and serialise with defaults for missing legacy fields. |
| 14 | whole file | No indexes are ever created, although the contract requires creating them at startup — this is the root cause of defects 6, 12 and 13. The remaining endpoints (punch-out, PATCH regularize, all four analytics, explain) are missing entirely. | `db.employees.getIndexes()` on a fresh database shows only `_id`. | `ensure_indexes()` on startup (idempotent), and implementations for all missing endpoints. |

## Looked at, and decided these were *not* defects

- **`load_dotenv()` + environment variables**: `load_dotenv` does not override variables already set in the process environment, so real env vars still win over `.env`, as the contract requires. Kept.
- **`compute_overtime`'s IST construction** (`datetime … replace(tzinfo=IST)`): attaching IST to a wall-clock time is the right idea for a non-overnight shift; the defects were the missing 30-minute rule and the missing overnight day-shift, not the time-zone approach. The replacement keeps the same idea, done from the attendance date.
- **Punch-in defaults**: `status` defaulting to `PRESENT` and storing `punch_out: None, work_hours: None, overtime_minutes: 0, half_day: False, history: []` matches DATA_MODEL.md exactly. Kept (with the status now restricted to the three presence values).
- **`int(seconds / 60)` in the helpers**: for positive durations truncation *is* floor, so that pattern itself was fine; the late defect was applying it before the grace comparison, not the truncation.
